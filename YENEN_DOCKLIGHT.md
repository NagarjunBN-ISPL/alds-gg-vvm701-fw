# Yenen DU1 (nozzle 1 + nozzle 2) — Docklight bench test

Docklight plays the **dispenser**; the VVM701 is the master and polls. Frames
below are generated by `tools/yenen_docklight.py`, which self-tests its TX
frames and payload layout against the vendor document before printing, so the
checksums are computed — not transcribed.

Firmware side: `src/yenen.c`, `yn_poll_nozzle()`.

---

## 1. Docklight / port settings

| Setting | Value | Source |
|---|---|---|
| Baud | **9600** | `YENEN_BAUD`, config.h:223 |
| Data / parity / stop | **8 / none / 1** | `yn_rs485_set_yenen_mode()` |
| Flow control | none | |
| Docklight mode | Send/Receive sequences in **HEX**, not ASCII | |

Paste the byte strings below straight into Docklight's sequence editor with
"HEX" selected — space-separated uppercase hex is the format it expects.

Timing: the firmware's read window is `RS485_RECV_TIMEOUT_MS` = 2000 ms, reset
on every received byte, with a 6 s hard deadline. A manual click within ~2 s of
seeing the poll is answered fine. It retries `YN_TOTAL_RETRIES` = 3 times,
300 ms apart, before declaring the nozzle silent and publishing `"data":"404"`.

## 2. TX — what the gateway sends (set these up as RECEIVE sequences)

Command 2 is the only command the firmware issues. It is byte-identical on
every poll, so one receive sequence per nozzle is enough.

| Name | Address | Bytes (10) |
|---|---|---|
| `POLL_NZ1` | DU1 NZ1, head 1 side A | `02 30 38 30 31 30 41 03 37 39` |
| `POLL_NZ2` | DU1 NZ2, head 1 side B | `02 30 38 30 31 35 41 03 37 3C` |

Layout: `STX '0' '8' '0' ('0'+head) <nzcode> 'A' ETX <ck_hi> <ck_lo>`.
Nozzle code is `'0'+(head-1)` for side A, `'5'+(head-1)` for side B.
Checksum = XOR of STX..ETX, emitted as **nibble+0x30** — so 0x7C becomes
`37 3C`, not `37 43`. That is the one place a hand-built frame usually goes
wrong.

---

## 3. RX — what Docklight answers (set these up as SEND sequences)

51 bytes each: `STX + 47 ASCII payload + ETX + 2 checksum`.

**All ten RX frames are byte-unique**, and the two TX polls differ, so nothing
in Docklight is ambiguous and every frame in the log identifies itself.

That costs one deliberate tweak. `NZ1_S4` is the "no activity since the last
poll" case, so its totaliser MUST equal `NZ1_S3`'s - that is the entire point of
the frame. Left alone the two come out byte-identical, so S4 carries a preset
volume of 10.00 L (`...6772 0000 1000...`) where S3 has zeros. Preset volume
takes no part in the sale derivation - the cloud differences totalisers,
Appendix B rule 2 - so S4 is still a valid zero-delta test, just distinguishable
on the wire. The generator asserts uniqueness before printing, so this cannot
silently regress.

Note this makes S4 differ by one field from the S4 in `YENEN_TEST_VECTORS.md`,
which keeps the byte-identical version because that is what a real pump sends.

Payload: `49 0<head> <nzcode> A <price:4> <preset_amt:4> <preset_vol:4>
<delivery_L:3> <delivery_amt:6> <total_L:6> <total_amt:8> <status:2> 0990`
— all values scaled x100. `status` is `00` idle, non-zero while dispensing.

## 4. How to run the test

1. Load `POLL_NZ1` / `POLL_NZ2` as receive sequences and all ten replies as
   send sequences.
2. Point each receive sequence's action at the matching `*_S0_IDLE_BASE` send
   sequence. That gives a self-running idle pump: every poll gets a valid
   baseline answer with no clicking.
3. To walk the sale scenario, drop the auto-answer for that nozzle and click
   the S1..S6 sequences by hand, one per poll, in order.
4. Watch the device log — `yn` tag prints both directions:
   `head1/A total TX (10 bytes): [...]` and `head1/A total RAW (51 bytes): [...]`.
   A rejected frame logs the reason (`no STX`, `no ETX+checksum`,
   `checksum mismatch`) instead of being silently dropped.

**Expected end state: exactly 3 transactions** — nozzle 1: 5.00 L/338.60 then
8.00 L/541.76; nozzle 2: 6.00 L/495.00.

| Wrong result | Likely cause |
|---|---|
| 5-6 transactions | status != `00` frames not filtered |
| 4 transactions | the S4 zero-delta frame creating a phantom sale |
| 2 transactions | nozzle 1 and 2 totalisers pooled instead of keyed per nozzle |
| negative delta | records processed out of TS order |

## 5. Two things the firmware does NOT check

Worth knowing before reading too much into a passing bench run:

- **The reply address is never validated.** `yenen_resp_valid()` checks STX,
  ETX + 2 trailing bytes, and the checksum — nothing else. Answering a NZ1 poll
  with a NZ2 frame is accepted and published under label 1. On a real bus the
  pump enforces this; Docklight will not.
- **The payload is never parsed on-device.** The raw 51 bytes go up as
  `"data"` and the cloud does all decoding and differencing. So this test
  validates the wire path and the cloud decoder, not any firmware-side maths —
  there isn't any.
